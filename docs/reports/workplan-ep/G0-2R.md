## 2. Token meter

- Reservation per batched call: `input_tokens_ub + max_tokens` (bytes bound plus output cap), priced at
  `max(input, cache_write_5m, cache_write_1h)` for input. After the call, the batch total uses the real usage
  (input + cache_read + cache_creation + output). A call with no usable usage stays at its reserved worst case
  (`unmetered_worst`).
- Usage above the reservation (60,000 input against 2,300 reserved): charge written at the true cost, `batch_stop`
  written, `BatchStopped` raised. Caught.
- `cache_creation_input_tokens = 1`, or only `cache_creation.ephemeral_5m_input_tokens = 1`: `BatchStopped`. Caught.
- Missing `output_tokens`, NaN, negative, bool, float, `usage: null`: charge at the reserved worst case,
  `batch_stop` then `overspent`, and every later reserve in the directory is refused. Caught.
- `input_tokens = 10**30`: `BatchStopped`. The recorded USD then blocks every ledger through the hard cap.
- `server_tool_use` is dropped silently and does not stop the batch. The client sends no `tools`, so the server
  cannot use any. Info only.
- Thinking: not sent. If it were sent, thinking is billed inside `output_tokens` and bounded by `max_tokens`.

**R1 (Medium, fix before the canary): overspent marker skipped for batched calls.** In `Ledger.charge` the batch-stop
branch raises `BatchStopped` before `if usd > reserved: self._overspend(...)` runs. Probe: true cost USD 0.006005
against USD 0.00055 reserved. The ledger gets `charge` and `batch_stop` but no `overspent`, and an unbatched ledger
in the directory then reserved normally. The USD 10 cap still holds, because the real charge counts. What breaks is
the documented rule that "recorded spend above the reserved worst case" stops every ledger in the directory.
Fix: when `usd > reserved`, write `overspent` (after or alongside `batch_stop`) before raising.

**R2 (Medium, fix before the canary or pin it in the launcher): re-entry without a batch.** The only other name a
stopped lineage accepts is `batch=None`. An unbatched ledger skips the batch caps, the per-call caps, the stop on
cache writes and the batch stops. Nothing forces the real host to use a batched ledger. Fix: in
`_check_pilot_ledger`, require `ledger.batch is not None` for `api.anthropic.com`. That conflicts with the
unbatched Sonnet canary in `G0-2-final.md`, so it depends on owner decision 4(a) in `ep1-design-notes.md`.

**R5 (Low): a second `charge` for one id overwrites the first.** `_sum` keeps the last charge per id. Probe: 2,200
tokens, then a second charge of 2 tokens, reported 2 batch tokens. `ClaudeClient` charges each id once, so this is
internal misuse only. Fix: refuse a charge for an id that already has one.

## 4. Bug hunt: `len(body)` in bytes as the input-token upper bound

**Why the bound holds.**
- A byte-level BPE token covers at least one UTF-8 byte of text, so tokens <= UTF-8 bytes.
- `json.dumps` uses `ensure_ascii=True`. Every non-ASCII character in the body is therefore 6 bytes (BMP) or 12
  bytes (astral), against 1 to 4 bytes of UTF-8. Every `"`, `\` and newline adds an escape byte.
- The envelope (`model`, `max_tokens`, `temperature`, role keys; about 120 bytes) is not tokenised. It covers the
  few formatting tokens the API adds per request and per message.
- Images and documents are refused by the client, and no `tools` are sent.
- What it depends on: a byte-level BPE with no Unicode normalisation that expands text (an NFKC-style expansion of a
  single code point could break it for non-ASCII), text-only content, no tools, and `ensure_ascii`. As defence in
  depth, usage above the reservation stops the batch after one call (see R1 for the overspent marker).
- Evidence limit: Claude's tokenizer is not public. I tested a pure-Python BPE with the GPT-2 rank file. No
  count_tokens call was made (it needs a key).

| Adversarial text | UTF-8 bytes | JSON bytes | GPT-2 tokens | UTF-8 bytes per token |
|---|---|---|---|---|
| English | 1,800 | 1,802 | 401 | 4.49 |
| Emoji incl. ZWJ, flags | 1,477 | 4,064 | 941 | 1.57 |
| CJK | 1,500 | 3,002 | 1,346 | 1.11 |
| Rare astral (CJK ext. B) | 1,200 | 3,602 | 1,198 | 1.00 |
| Base64 | 2,000 | 2,002 | 1,525 | 1.31 |
| JSON, many short tokens | 2,161 | 2,643 | 1,123 | 1.92 |
| Single chars, spaced | 1,999 | 2,029 | 1,000 | 2.00 |
| Punctuation | 2,000 | 2,124 | 1,572 | 1.27 |
| Control chars | 500 | 2,638 | 499 | 1.00 |

Rare astral characters and control characters reach exactly 1.00 UTF-8 bytes per token. The margin there comes from
JSON escaping (3 to 5x). Tokens <= bytes held in every case.

**Does a 2,000-byte cap make EP-1 impossible? No.** Measured with the real `prompts/ep1/system.md` (460 B), `turn.md`
(269 B) and `team_claude.prompt`, worst case over the 15 heldout sets:

- Round 2, card A or its neutral twin (237 B), all 4 claims held, a 49-character `refused:` status: **1,386 bytes.**
- With a card at `MAX_CARD` (600 B): **1,749 bytes.**
- Round 1: 1,223 bytes.

The cap leaves at least 251 bytes of headroom. `team_claude` refuses an oversize body before the client does
(`PromptTooLarge`).

**Recommended resolution: keep the strict bytes bound and 2,000.** It is stricter than the prereg's "2,000 input
tokens". Record in the prereg that the per-call input cap is 2,000 **request bytes**, a strict upper bound on tokens.
Add an assertion that EP-1 prompt text is ASCII (it is today), which removes the normalisation caveat. No
bytes-per-token factor is needed, and none is justified without Claude's tokenizer.

**Worst-case EP-1 schedule at Haiku 5.5 sheet prices** (input 0.10, output 0.50, 1h cache write 0.20 per million;
the reservation prices input at 0.20):

| Option | Per call | 480 calls | 500 calls | Canary + 499 calls |
|---|---|---|---|---|
| A: bytes bound, 2,000 / 300 (recommended) | USD 0.00055 | USD 0.264 | USD 0.275 | 0.00415 + 0.2745 = USD 0.279 (20 k canary); 0.01815 + 0.2745 = USD 0.293 (90 k canary) |
| B: 4,000-byte budget / 300 (not needed) | USD 0.00095 | USD 0.456 | USD 0.475 | the token cap would have to be 500 x 4,300 = 2.15 M |

- At 10x the input and output prices, option A bills at most USD 1.75 for 500 calls, under the USD 5 cap.
- Realistic spend, from the 1,386-byte maximum, is at most USD 0.139 for 480 calls, likely about USD 0.04.
- The prereg's USD 0.18 uses the 0.10 input price. The code reserves at 0.20, so the reservation is USD 0.275.
  Correct the text.

## 5. Canary size

**Assumption:** the Console shows cost to USD 0.01 (cents). If it shows more decimals, smaller is enough.

**What makes a 10x error visible.** With N actual input tokens, the cost is N x 0.10/M at the sheet price and N x
1.00/M at a Haiku-4.5-like price. For the 10x case to be at least 2 display units (USD >= 0.02), N must be at least
20,000. For the correct price to still show USD 0.00 (< 0.005), N must be below 50,000.

**The current cap cannot reach that.** `canary_input_tokens_max = 20,000` limits `ub` (bytes) to 20,000, so
N <= 20,000. Realistic padding gives N of about 4,000 to 10,000 (2 to 5.3 bytes per token measured), so the 10x cost
is USD 0.004 to 0.01. That is not reliably visible. The 90,000-byte figure in `spend-canary-plan.md` and
`G0-2-final.md` is refused by the current code.

**Recommendation, as an owner option (design notes decision 4b), not a cap raise:**
- `canary_input_tokens_max` 90,000; canary `tokens` cap 90,300.
- USD 0.05 and 1 call unchanged.
- Worst case 90,000 x 0.20/M + 300 x 0.50/M = USD 0.01815.
- `ub` stays below the 100,000-token long-context threshold.

Pad with plain words. At the measured 2.0 to 5.3 bytes per token, 90 KB gives N of about 17,000 to 45,000. At the
low end (5.3 bytes per token, English words) the 10x cost is about USD 0.017, under 2 units. So pad with short
spaced tokens: lower-case letters or numbers, measured at 2.0 to 2.6 bytes per token, which gives about 30,000 to
40,000 tokens. That is USD 0.003 to 0.004 at the sheet price (shows 0.00) and USD 0.03 to 0.04 at 10x. The exact token
counts in the Console are compared first; the cost check is for the price only.

**Cost to EP-1:**
- The canary counts inside the `ep1` token cap.
- If the canary charge went missing (which stops the program anyway), 90,300 reserved tokens would leave
  (1,150,000 - 90,300) / 2,300 = 460 worst-case `ep1` reservations, fewer than 480.
- After a normal charge (about 35,000 real tokens), 484 remain, and `ep1` calls are metered at real usage (about 500
  tokens each). This is fine in practice, but the prereg's "19 spare calls" holds only on real usage, not on
  worst-case reservations. With the 20,000 cap the probe gave 491.
- A Sonnet canary cannot use the canary batch with any useful padding (USD 0.05 allows at most about 11,750 bytes),
  and the canary batch allows only one call. Sonnet-then-Haiku in one batch is impossible. That needs owner
  decision 4(a).
